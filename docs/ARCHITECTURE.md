# 架构:reBot Copilot 设计模式

**这份文档是产品架构的锚点 —— 设计模式的唯一家。**

它只回答一个问题:**这台机器是什么、概念怎么组织、层次怎么分**。它不回答:

- 交互骨架的布局/流程/接口 → [`docs/INTERACTION.md`](./INTERACTION.md)
- 硬件数值与已验证事实 → [`docs/HARDWARE_NOTES.md`](./HARDWARE_NOTES.md)
- 当前进度与阻塞 → [`PROGRESS.md`](../PROGRESS.md)
- 怎么使用与部署 → [`README.md`](../README.md)
- 历史决策的来龙去脉 → issue #1(历史记录,不再追加;新决策写这里)

**设计模式的先后:先立骨架(本文件),插件(具体动作实现)后做。** 骨架没立住就谈插件是本末倒置。

骨架已落地(见 [`INTERACTION.md`](./INTERACTION.md)),插件层也已落地 —— 扩展点怎么用看 [`PLUGINS.md`](./PLUGINS.md)。本文件仍只讲概念,不讲接口。

## 一句话定位

**通用可编程空间定位平台。**

卖的不是"摄影臂",是**"把任意空间位置+姿态变成可一键到达、稳定保持、可编程触发的资源"**。摄影是这个资源的第一个实例,不是产品的全部 —— 产品摄影、3D 扫描、质检巡检、布光、示教回放、可编程工装,都是同一套内核上的不同组装。

## 三个不变量(骨架,永不动)

```
① 内核 Kernel        空间定位能力:move_to / hold / settle / 急停 / 安全闸门
                      —— 场景无关,是物理地基,永不动

② 交互骨架 Skeleton   锚点库 / 导航(到位) / 触发(动作) / 编排(可选)
                      —— 场景无关,一份界面,所有用户共用

③ 插件 Plugins        动作的具体实现:快门 / 夹爪 / 传感器 …
                      —— 场景相关,可插拔,后做
```

**模式的先后就是这三层的先后**:内核是地基(已有),交互骨架是承重结构(先设计),插件是装修(后做)。插件随时换,骨架不能塌。

## 概念模型:四个无领域积木

| 积木 | 定义 | 性质 |
|---|---|---|
| **锚点 Anchor** | 一个命名的"位置+姿态",拖臂录制 | 最小单元 |
| **动作 Action** | 末端负载的可触发操作(抽象接口) | 插件的挂载点 |
| **集合 Collection** | 锚点的组织容器,用户自己分组命名 | 容器 |
| **编排 Sequence** | 锚点+动作的自动流程 | 可选,高级 |

**场景 = 用户用积木组装出来的结果,不是产品预设的模式。**

像 Notion:底层是无领域含义的积木,普通人当笔记本、仓库管理员搭成设备库,产品里**没有"模式切换"**。同理,产品**不知道、也不关心**一个锚点叫"机位"还是"工位" —— 那是用户起的名字。每个部署实例被一个用户组装成固定形态,之后就固定在那个形态里用,永不切场景。

## 配置与使用分层

```
配置层(偶尔,像 Notion 搭页面)      使用层(天天,像 Notion 用页面)
  拖臂 → 录锚点                       点锚点 → 臂到位 → 触发动作
  配动作 / 起名 / 编排                 停住,继续下一个
```

摄影师搭好"四方位"后很少回配置层;日常就在使用层点锚点、触发。**使用层的主交互极简:点锚点 → 到位 → 稳定 → 触发 → 继续**。这是整个产品形态的原子操作,也是所有场景的公共闭环。

## 模板机制(解决低门槛)

模板 = **预组装好的起步包**(如"产品拍摄"模板 = 四方位锚点 + 快门动作)。

关键性质:**模板进了用户手里就溶解成通用积木** —— 可改、可删、可从空白重搭。模板是快捷起步,不是封闭模式。这区分于"场景切换":场景是个封闭盒子,用户只能在盒子里操作;模板是别人搭好的积木,用户可以接着搭。

## 词汇基调

全界面**中性词**,不出现领域词:

| 用 | 不用 |
|---|---|
| 锚点 | 机位 / 方向 / 点位 |
| 触发(动作) | 拍照 / 连拍 |
| 集合 | 序列 / 脚本 |
| 编排 | 播放列表 / 程序 |

领域词由用户起名时自己用("这个锚点叫正面")。**界面词汇基调就是"锚点"**。

## 模式的先后边界

- **先定**:概念模型、分层、词汇(本文件)—— 骨架
- **后做**:插件(ESP32 快门是第一个动作插件)、场景模板 —— 骨架下的填充

两者都已落地。插件层收敛成**三个扩展点而不是一个 hook 链**:动作插件(进程内,流程会等它)、触发源(进程外 HTTP 客户端)、事件订阅(进程外 WS 客户端)。为什么是三个、为什么触发源不能是进程内回调,见 [`PLUGINS.md`](./PLUGINS.md)。

摄影场景需要的"单次到位+拍"(点锚点 → 到位 → 稳定 → 触发 → 停住)是**使用层原子操作的最小闭环**,也是所有场景的公共操作,先于任何插件存在。

## 模式的对错,由摄影场景验证

这个模式是从摄影场景倒推收敛的,它的试金石是:**摄影场景能否用这四个积木 100% 表达出来,且不为"通用"付任何专用税**。能,模式成立;不能,说明抽象漏了东西 —— 那就修抽象,不是给摄影开后门。
